## Найденные причины

Для каждой проблемы: воспроизведение → причина → исправление → проверка.
------------------

--- Причина --- 
В `TicketPanel.jsx` внутри `useEffect` нет механизма отмены или игнорирования устаревших запросов. Если запрос для заявки `A` выполняется дольше, чем для `B`, ответ `A` приходит позже и перезаписывает состояние.

## Одновременное редактирование

Что произойдёт при изменении одной заявки двумя сотрудниками?
-----------------
При одновременном редактировании двумя сотрудниками последний завершившийся запрос перезапишет результат предыдущего, а в истории появятся две записи. 
Для полноценной защиты требовалось бы добавить optimistic locking (проверку версии) или блокировку строки (`FOR UPDATE`), но это выходит за рамки обязательных требований задания.

## Оставшиеся ограничения

Что не закончено и что сделали бы следующим?
-----------------

**1. Одновременное редактирование двумя сотрудниками**  
Сейчас работает стратегия «последний выигравший». 
Не реализованы optimistic locking (поле `version` или сверка `updated_at`) и pessimistic locking (`SELECT ... FOR UPDATE`). 
Следующим шагом добавил бы optimistic locking: клиент отправляет текущий `updated_at`, сервер сравнивает с актуальным и при несовпадении возвращает `409 Conflict` с предложением перечитать карточку.

**2. Надёжность и отказоустойчивость**
* **Error boundaries в React** — сейчас падение одного компонента роняет всё приложение. Добавил бы `<ErrorBoundary>` вокруг `TicketPanel`.
* **Retry logic для сетевых запросов** — при временных сбоях сети (5xx, timeout) автоматический повтор с exponential backoff.
* **Предупреждение о несохранённых изменениях** — `beforeunload` и блокировка перехода, если пользователь выбрал новый источник, но не нажал «Сохранить».

**3. UX и доступность**
* **Индикатор конфликта** — если пока пользователь редактировал, источник изменил кто-то другой, показать уведомление и предложить перечитать.
* **a11y-аудит** — проверка aria-атрибутов, фокус-менеджмента, навигации с клавиатуры (сейчас минимально).
* **Toast-уведомления** вместо статичных сообщений об успехе/ошибке.

**4. Масштабируемость и производительность**
* **Пагинация/фильтрация списка заявок** — сейчас грузится всё сразу, при тысячах записей будет тормозить.
* **Индексы в БД** — добавить на `tickets.status`, `tickets.source_id`, `tickets.updated_at` для будущих фильтров и сортировок.
* **Кэширование справочника источников** — сейчас запрашивается при каждом рендере; можно загрузить один раз и хранить в контексте.

**5. Тестирование и инфраструктура**
* **Unit-тесты на PHP** (PHPUnit) — сейчас есть только интеграционные Python-тесты. Добавил бы тесты для `TicketRepository` с моками БД.
* **Миграции БД** — сейчас схема в одном SQL-файле, нет версионирования. Перешёл бы на простой миграционный подход (нумерованные файлы `003_*.sql`).
* **CI/CD pipeline** — автоматический запуск `smoke.py` и `test_fixes.py` в GitHub Actions при пуше.
* **Линтеры** — PHP-CS-Fixer, ESLint/Prettier для единообразия кода.

**6. Аудит и безопасность**
* **Журнал входов/выходов** — сейчас история только по источникам, нет аудита сессий.
* **Rate limiting** на `/api/demo/login` и `/api/tickets/{id}/source` для защиты от брутфорса.
* **Мягкое удаление заявок** (`deleted_at`) вместо физического — для восстановления и аудита.

**Приоритет следующих шагов** (если бы продолжил работу):
1. Optimistic locking — самая высокая бизнес-ценность при минимальных усилиях.
2. Error boundaries + предупреждение о несохранённых данных — критично для UX.
3. Unit-тесты на PHP — повышают уверенность при будущих изменениях.
4. Пагинация и индексы — готовность к росту данных.

Остальное (CI/CD, миграции, линтеры) — инфраструктурные улучшения, которые важны для команды, но не блокируют работу модуля.
